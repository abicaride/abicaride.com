# Abi Website Design Publisher

A local, dependency-free Figma development plugin that publishes
repository-owned design decisions into bounded Figma sections.

The repository is the source of truth. The plugin is a release mechanism:

```text
Astro code + design docs + production tokens
  → package
  → validate
  → publish tagged Figma sections
  → visually verify
```

Figma remains useful for visual communication, review and exploration, but is
not an independent implementation source or an Astro build dependency.

## Ownership model

- `src/styles/tokens.css` owns production design tokens.
- `src/i18n/config.ts`, `src/data/` and content collections own public copy and
  structured content.
- `src/components/` and `src/components/pages/` own implemented composition and
  behaviour.
- `docs/design/` records durable design decisions and rationale.
- `design-release.json` names the current design release and its Figma targets.
- `code.js` renders managed Figma references and preserves historical
  exploration commands.
- `dist/code.js` is generated by `package.mjs`; do not edit it directly.

The local publisher owns Foundations, implemented-component documentation,
production-page snapshots, design/research summaries and bounded approved or
archived references. The packaged release includes the production favicon
vector, hero and About portrait, so publishing does not depend on MCP quotas or
manual image imports.

## Why the release runs in Figma Desktop

The local development plugin is the supported Figma write path. It deliberately
does not depend on Figma MCP availability or free-tier quota: packaging and
validation happen in the repository, then Figma Desktop executes the packaged
code using the signed-in editor's existing access.

This is not a shortcut around permissions. The user must already be able to edit
the target file, and the plugin validates the expected file and page before it
writes. No Figma credential is stored in GitHub, Codex, the plugin bundle or CI.
MCP can still help inspect a file, but a design release must remain possible
without it.

## Status model

Every newly generated root section receives one unambiguous status:

- `[CURRENT]` — generated from or synchronized with the implemented site.
- `[APPROVED]` — an approved design reference that is not the production
  baseline itself.
- `[ARCHIVE]` — superseded exploration or historical material.

The section also stores private plugin metadata containing the design release,
source Git commit and repository source-of-truth statement.

## Current publishing commands

- **Publish current Foundations** creates or replaces the managed production
  Foundations section. Its palette is injected from `src/styles/tokens.css`
  and its approved favicon from `public/favicon.svg` during packaging,
  preventing duplicated Figma token values or brand-mark vectors from drifting.
- **Publish current Components reference** documents only patterns already
  reused in Astro: localized navigation, primary and secondary actions, project
  previews, analytics consent, back-to-top and the contact footer.
- **Publish current Moodboard direction** replaces the managed V2 research
  summary with the implemented positioning, homepage structure and remaining
  content questions.
- **Publish current Homepage snapshot** creates or replaces the editable
  production Homepage reference with the packaged hero image.
- The shared footer reference includes its contact close, approved brand-mark
  watermark, identity signature, labelled privacy/language/build utilities and
  stacked mobile treatment.
- **Publish current imaginArt snapshot** creates or replaces the editable
  production case-study reference, including the public evidence caveats.
- **Publish current About snapshot** creates or replaces editable desktop and
  mobile references with the packaged About portrait.
- **Publish current Contact snapshot** creates or replaces editable desktop and
  mobile Contact references on the shared About + Archive page. The separate
  managed root preserves the current About, approved references and archives.
- **Prepare this Foundations page for public viewing** removes only the known
  Figma starter tutorial, obsolete workspace-intro frames and the redundant
  top-level hero-reference import from the three Foundations pages. It also
  clears leftover prototype start labels such as `Start here`. It places
  the current Foundations/Components reference at the origin and orders the
  approved Exploration first, followed by its named archives. Run it once per
  Foundations page after an explicit cleanup request.

`01 — Foundations` is intentionally a single-reference page: once the managed
`[CURRENT]` Foundations section exists, this maintenance command removes every
other loose top-level object on that page. This catches the icons, text samples
and image layers left behind by Figma's starter tutorial. Components and
Explorations retain the narrower exact-name allowlists described above.

Use the commands only in these destinations:

| Figma file | Page/canvas | Current command |
| --- | --- | --- |
| Abi Website Foundations | `01 — Foundations` | Publish current Foundations |
| Abi Website Foundations | `02 — Components` | Publish current Components reference |
| Abi Website Moodboard | FigJam canvas | Publish current Moodboard direction |
| Abi Personal Website | `01 — Homepage` | Publish current Homepage snapshot |
| Abi Personal Website | `02 — Case Studies` | Publish current imaginArt snapshot |
| Abi Personal Website | `03 — About + Archive` | Publish current About snapshot |
| Abi Personal Website | `03 — About + Archive` | Publish current Contact snapshot |

Existing plugin-generated final directions remain `[APPROVED]` references.
Older A/B/C/D, wireframe and reframing commands remain available under
**Archive** so their history is reproducible. MCP is optional and is not part
of the release path.

## Release workflow

1. Make and validate the intended Astro/design changes.
2. Commit the repository state that should be represented in Figma. A packaged
   `+working-tree` source is suitable for a visual preview, but repackage from
   the intended commit before treating Figma as synchronized.
3. Package the local plugin:

   ```sh
   npm run figma:package
   ```

4. Run the complete dependency-free publisher validation:

   ```sh
   npm run figma:validate
   ```

5. Import or refresh `manifest.json` in Figma Desktop.
6. Open the exact target page and run the relevant **Publish current** command.
7. Run the Homepage, imaginArt, About and Contact production snapshot commands
   in the appropriate Personal Website pages.
8. Verify the generated output visually before treating the release as
   synchronized. Check the status/release label, the represented content,
   separation beyond the existing rightmost canvas item and the survival of all
   untagged, `[APPROVED]` and `[ARCHIVE]` work.

For a public-canvas cleanup, open each of `01 — Foundations`,
`02 — Components` and `03 — Explorations`, run **Prepare this Foundations page
for public viewing**, and visually verify each page. This command is deliberately
separate from normal publication because it removes a small exact allowlist of
historical starter/intro layers and rearranges named top-level references.

Packaging embeds the current Git commit, literal production color tokens, the
production favicon and transparent brand-mark vectors, and the two production
portrait images into `dist/code.js`. Checking out an older commit, repackaging
and republishing provides a reproducible rollback path; Figma version history is
a second safety net.

## Safety model

- The plugin has no network access or external dependencies.
- It validates the open Figma file, editor type and page before writing.
- Generated roots are tagged with private plugin data.
- Current/approved commands build a replacement before removing only their own
  previously tagged predecessor.
- Production snapshots recalculate their position against every visible
  top-level canvas item and sit beyond the rightmost edge, so archived,
  approved and manually arranged work cannot be covered by a release.
- Normal publishing commands never modify untagged manual frames, references,
  comments or experiments. The explicit public-canvas cleanup command is the
  sole exception: it removes its documented starter/intro allowlist on the
  three exact Foundations pages, plus every loose top-level object other than
  the managed `[CURRENT]` section on the intentionally single-reference
  `01 — Foundations` page.
- Historical exploration commands do not delete earlier work.
- Figma Undo can reverse a local publisher execution immediately.
- Personal photographs are packaged directly from the two repository-owned
  production source images. The publisher does not generate or retouch a
  likeness.

Running a current command is an external write: after the new tagged section is
created, the command removes its own previous tagged section. It must therefore
be run only for an explicit Figma publish/synchronization request. It never
implies a website deployment, permission change or publication to the Figma
Community.

## Recovery

If a generated section is incomplete, overlaps other work or appears in an
unexpected location:

1. use Figma Undo immediately when practical;
2. confirm the file, page and command against the table above;
3. fix the repository source or `code.js`—never `dist/code.js` and never the
   generated `[CURRENT]` section by hand;
4. run `npm run figma:package` and `npm run figma:validate`;
5. rerun the current command and visually verify it again.

If an older synchronized state is required, check out that repository commit,
package it and republish it. Figma version history remains an additional safety
net, not the primary source of truth.

## Historical image layers

Some historical approved-reference commands reuse image fills already present
in the open Figma file:

- `hero-approved-reference.jpg` on Foundations, sourced from
  `docs/design/references/hero-approved-reference.jpg`.
- `AbileneHero` on the legacy final-direction exploration page.
- `AbileneAbout` on About + Archive.

If one of those historical layers is absent, the publisher creates a labelled
neutral slot. Current Homepage and About snapshots use the packaged production
images and do not require these layers.

## Install locally

Local development plugins require Figma Desktop.

1. Run `npm run figma:package`.
2. Open an editable Figma file.
3. Choose **Plugins → Development → Import plugin from manifest…**.
4. Select this directory's `manifest.json`.
5. Run **Abi Website Design Publisher** from the Development menu.

The plugin stays local to the computer where it is imported and does not need
to be published to the Figma Community.

## Maintenance

Update the authoritative Astro/content/design source first. Change Figma-only
layout rendering in `code.js` only when the publisher itself needs to present
that source differently. Bump `design-release.json` for a meaningful new design
release, then package, validate, publish and visually verify.

The detailed imaginArt factual blueprint remains in
[`docs/content/case-study-imaginart.md`](../../../docs/content/case-study-imaginart.md);
the publisher deliberately summarizes rather than duplicates it.
